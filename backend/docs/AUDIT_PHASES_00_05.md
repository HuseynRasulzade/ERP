# Verification audit — Phases 0–5 (spec numbering)

This audit checks the six foundation specs (`phase00.txt` … `phase05.txt`)
against the code and tests as they stand. The repo README numbers things
differently, so each spec is matched to the code by content:

| Spec | Content | Where it lives in this repo |
|---|---|---|
| Phase 0 | Architecture and foundation core | README "Phase 0": `src/{tenant,identity,rbac,document-framework,document-link,numbering,period,audit,currency,settings,idempotency,foundation-test-document}` |
| Phase 1 | Organization and business structure | README "Phase 1": `src/org-structure` |
| Phase 2 | Nomenclature / master data | README "Phase 2" (`src/product-catalog`) plus unit conversions and prices from README "Phase 3" (`src/counterparty-pricing`) |
| Phase 3 | Partners, counterparties, contracts | README "Phase 3" (`src/counterparty-pricing`) plus `src/counterparty-contracts` and `SupplierProductCode` (`src/procurement`) |
| Phase 4 | Accounting core and the AZ chart of accounts | "Accounting Core": `src/accounting-core` (docs/ACCOUNTING_CORE.md) |
| Phase 5 | Tax engine and AZ localization | "Tax Engine": `src/tax-engine` (docs/TAX_ENGINE.md) |

Status labels: **Done** means implemented and covered by a test. **Partial**
means it is implemented but narrower than the spec, or not tested. **Missing**
means it is not implemented. **Fixed** means it was Missing or Partial before
this audit and is now fixed and tested in `test/audit-phases-00-05.e2e-spec.ts`,
the "audit spec" below. File paths are relative to `backend/`.

### The flaky numbering test: root cause

supertest calls `server.listen(0)` lazily when a request targets an HTTP
server that is not yet listening. As soon as **that request** finishes, it
calls `server.close()`. Since Node 19, `close()` also destroys idle and
just-accepted keep-alive sockets. With 60 concurrent requests, the first one to
finish tore down connections whose requests had not been parsed yet, which
produced `read ECONNRESET`. The cause is in the test harness, not in the
numbering engine. The engine itself uses `SELECT … FOR UPDATE` on the sequence
row and never produced a duplicate. The fix binds the server once in
`beforeAll` (`await app.listen(0)`). supertest then reuses it and never
closes it; `app.close()` closes it at the end. The test was not skipped or
weakened: it still asserts 60 × `201` and 60 distinct numbers.

## Known pre-existing drift (not introduced here)

`prisma migrate diff --from-migrations … --to-schema-datamodel …` reports a
cosmetic default-expression difference on `settings.valid_from`
(`'1970-01-01'::date` vs `'1970-01-01'`). It predates this audit. The audit
migration adds only triggers and exclusion constraints, which Prisma does
not model, so it adds no drift.
